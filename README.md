# Pathology Clinical Summary (Prototype)

A clinical information summary dashboard for pathologists. When a pathologist
selects a pathology accession from a worklist, the app retrieves and
summarizes clinically relevant patient information — prioritized for
interpreting the specimen currently on the bench.

**Version 1 uses synthetic data only.** It does not connect to any real
hospital system, EMR, LIS, RIS/PACS, or real patient data. No LLM is used —
the Korean clinical summary is generated by a deterministic rule-based
engine and template renderer.

## Project purpose

Pathologists frequently need to interpret a specimen in light of a patient's
prior pathology, chronic disease history, medications, procedures, imaging,
and labs — scattered across many systems. This prototype demonstrates a
single-pane clinical context view built around one core idea: **relevance
to the current case is config-driven, not hard-coded**, so the same UI and
engine can be extended to new organs/diseases by editing data, not code, and
can eventually be pointed at real hospital systems without a UI rewrite.

## Architecture

```
UI (React components)
   │
   ▼
ClinicalDataService              — the only thing components talk to
   │
   ▼
ClinicalDataProvider (interface) — src/providers/ClinicalDataProvider.ts
   │
   ▼
MockClinicalDataProvider         — Version 1's only implementation
   │
   ▼
synthetic data (src/mock/*)
```

Relevance and summary generation sit beside the UI, not inside it:

```
ClinicalDataService.getPatientCaseBundle(accessionNumber)
        │
        ▼
RuleBasedClinicalRelevanceService.evaluate(...)   — src/services/relevance
        │  (matches clinicalRelevanceProfiles.ts against the current case,
        │   ranks every record highest/high/important)
        ▼
TemplateBasedClinicalSummaryService.generate(...) — src/services/summary
        │  (renders the Korean clinical summary from real fields only —
        │   never fabricates, always distinguishes "not documented" from
        │   a documented negative)
        ▼
UI sections (ClinicalSummaryPanel, PreviousPathologySection, ...)
```

Key architectural rules enforced throughout the codebase:

- **Components never import mock data.** Everything goes through
  `ClinicalDataService`, which owns a `ClinicalDataProvider`.
- **No disease-specific branching in components or the relevance engine.**
  What labs/external reports matter for a given organ or disease lives
  entirely in `src/config/clinicalRelevanceProfiles.ts`.
- **"Not documented" is never collapsed into "absent."** Procedure/surgery
  findings use a three-state `PresenceStatus` (`present` / `absent` /
  `not_documented`); summary sections that have no data say so explicitly
  instead of rendering blank or inferring a negative.
- **Any previous malignancy stays top priority regardless of organ** — it
  may represent metastasis, so the relevance engine and the previous
  pathology table both pin it into the highest-priority group even when
  the malignant record is from an unrelated organ.

### Canonical model and future hospital integration

```
Hospital EMR/LIS/RIS  →  adapter  →  canonical model (src/models)
                                   →  ClinicalDataProvider implementation
                                   →  ClinicalDataService
                                   →  relevance/summary services
                                   →  UI
```

`src/models/` defines the canonical shape every clinical fact is expected to
fit (with `Provenance` on every record). FHIR/HL7 mapping is intentionally
**not** implemented in Version 1 — the boundary is just kept clean so a real
adapter can be added later without touching the UI or the relevance/summary
services. See "Replacing the mock provider" below.

## Mock data design

All synthetic data lives under `src/mock/` as plain TypeScript arrays,
keyed by `patientId` / `accessionNumber`, with small lookup helpers
(`getDiagnosesForPatient`, `getPreviousPathologyForPatient`, etc.) —
deliberately shaped like what a real REST response would look like once
`MockClinicalDataProvider` is replaced.

- **15 synthetic patients, 15 worklist accessions, ~25 pathology records
  total** (worklist + historical previous-pathology records combined),
  covering: kidney transplant, native kidney biopsy, MGRS/monoclonal
  gammopathy, gastric cancer, liver mass/previous HCC, two appendectomy
  variants (one with documented perforation/peritonitis, one without),
  lung biopsy with previous colon cancer, liver lesion with previous breast
  cancer, colon cancer, prostate cancer, lymph node/lymphoma workup, plus
  lighter-weight skin/thyroid/bone-marrow cases.
- External document placeholders (`public/mock-assets/`) are a hand-built
  minimal valid PDF and a schematic SVG "gel image" — clearly labeled as
  synthetic, never real scanned content.
- Every record carries a `provenance` field (`sourceSystem`,
  `sourceRecordId`, `recordedAt`) even though Version 1's source system is
  always `MOCK_EMR`/`MOCK_LIS`/`MOCK_RIS` — this is what a real adapter
  would populate with the actual hospital system identifiers.

## How to add a new clinical relevance profile

Open `src/config/clinicalRelevanceProfiles.ts` and add one entry to the
array:

```ts
{
  id: 'my-new-profile',
  name: 'My Disease (한글명)',
  match: {
    organ: ['pancreas'],
    suspectedDisease: ['pancreatic cancer', 'ipmn'],
  },
  relevantLabTestCodes: ['CA19_9', 'AMYLASE'],
  relevantExternalReportTypes: ['MOLECULAR_REPORT'],
  priority: 'highest',
}
```

- `match` fields are matched as case-insensitive substrings against the
  current case's organ/site, specimen, procedure, and submitted clinical
  information. A profile matches if **any** populated field matches.
- Multiple matching profiles are merged (lab test codes and external report
  types deduplicated) by `RuleBasedClinicalRelevanceService` — you don't
  need to worry about overlap with existing profiles.
- Lab test codes referenced here must exist as `testCode` values in your
  data source (see `src/mock/labResults.ts` for the current set); no other
  file needs to change.
- No component or service file needs to change — the lab results section,
  the summary's lab-trend section, and the external documents section all
  read `relevantLabTestCodes` / `relevantExternalReportTypes` from the
  relevance engine's output.

## How to add a new external report type

1. Add the literal to the `ExternalReportType` union in
   `src/models/externalDocument.ts`.
2. Add one entry to `externalReportDefinitions` in
   `src/config/externalReportDefinitions.ts` (label, category, viewer type
   — `'image'` or `'pdf'`).
3. Reference the new type from any `ClinicalRelevanceProfile.relevantExternalReportTypes`
   that should surface it, and from any `ExternalClinicalDocument.reportType`
   in your data source.

The relevance profile decides **when** a report type matters for a case;
`externalReportDefinitions.ts` decides **what** the report type is
(label/category/viewer). Keeping these separate is what let DSA and
immunofixation/electrophoresis/flow-cytometry/etc. all share one generic
`ExternalClinicalDocument` model instead of DSA-specific code.

## How a future hospital EMR/LIS/RIS adapter would replace MockClinicalDataProvider

1. Implement `ClinicalDataProvider` (`src/providers/ClinicalDataProvider.ts`)
   against real systems — e.g. `HospitalClinicalDataProvider`, internally
   composing EMR/LIS/RIS/PACS-specific adapters that translate hospital data
   into the canonical models in `src/models/`.
2. Populate `Provenance.sourceSystem` / `sourceRecordId` with the real
   source system and record identifiers instead of the `MOCK_*` values.
3. In `src/App.tsx`, change one line:
   ```ts
   const clinicalDataService = new ClinicalDataService(new HospitalClinicalDataProvider(...));
   ```
   No other file changes — `ClinicalDataService`, the relevance/summary
   services, and every React component are written against the
   `ClinicalDataProvider` interface and canonical models, not against the
   mock implementation.
4. If the hospital source exposes FHIR/HL7, that mapping lives entirely
   inside the new adapter/provider layer — it never leaks into the UI or
   the relevance/summary services, which is the reason that boundary was
   kept clean in Version 1 even though FHIR/HL7 support itself is out of
   scope here.

## Safety notes

- No real patient data, real hospital connections, OCR, or automatic
  interpretation of scanned/external documents (DSA, immunofixation, etc.)
  is implemented — the app only surfaces that a relevant document exists
  and lets the pathologist open the original.
- The summary service never infers a missing finding as negative, never
  infers medication indications that aren't explicitly documented, and
  never auto-diagnoses metastasis.
